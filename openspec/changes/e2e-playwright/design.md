# Design

## Context

See proposal.md. The API reads `EB_API_URL`, `EB_APPLICATION_ID`, `EB_PRIVATE_KEY_PATH`, `PUBLIC_URL` and
`DATABASE_URL`; it signs requests to Enable Banking with an RS256 JWT and sends the browser to the URL returned by
`POST /auth`, expecting a redirect back to `<PUBLIC_URL>/api/banks/callback?code=…&state=…`.

## Goals / Non-Goals

**Goals:** a one-command, isolated, repeatable e2e run that exercises the real stack, including the bank flow.

**Non-Goals:** CI; testing Enable Banking itself; pixel comparisons.

## Decisions

### Stack
`e2e/compose.yaml`, project `cheles-e2e`, own network, nothing shared with `cheles`:
- `db`: `postgres:16-alpine` on tmpfs.
- `fake-eb`: `python:3.12-alpine` running `e2e/fake-enable-banking/server.py` (standard library only), published on
  `127.0.0.1:3101` because the browser visits its authorization page.
- `api`: built from `../cheles-backend`, with `EB_API_URL=http://fake-eb:8080`, `PUBLIC_URL=http://127.0.0.1:3100`, a
  throwaway key pair generated by the global setup and mounted as the secret.
- `web`: built from this repo with the default build-time `API_URL=http://api:8000`, but **run** with
  `API_URL=http://nowhere.invalid`, so «API URL fixed at build time» holds on every run; published on `127.0.0.1:3100`.

### Fake Enable Banking
Routes: `GET /aspsps`, `POST /auth` (returns `http://127.0.0.1:3101/authorize?state=…`), `GET /authorize` (303 to the
callback with `code=e2e-code`), `POST /sessions` (two accounts: «Cuenta Online» and «Ahorro», with IBANs), `DELETE
/sessions/{id}`, `GET /accounts/{uid}/balances`, `GET /accounts/{uid}/transactions` (salary, supermarket, restaurant
and a transfer to the savings account, dated in the current month relative to today). It ignores the JWT.

### Global setup and teardown
Setup generates the key pair with Node's `crypto`, runs `docker compose -p cheles-e2e up -d --build --wait`, creates the
user with the API's own `create_user` use case through `docker compose exec`, and stores the TOTP secret for the tests
(`otpauth` computes codes). Teardown runs `down -v`. `E2E_KEEP=1` keeps the stack for debugging.

### Meta-test
`tests/spec-coverage.test.ts` also reads test names from `e2e/*.spec.ts`; the exemption list keeps only «Access from
another device».

### Layout and tooling
`playwright.config.ts` (Chromium, mobile viewport, `es-ES`, `Europe/Madrid`, one worker: the tests share one user and
stack), `e2e/*.spec.ts`, screenshots to `e2e/screenshots/` (git-ignored). Vitest keeps ignoring `e2e/`; Biome and `tsc`
include it.

## Risks / Trade-offs

- [Slow: two image builds] → Local and on demand only; Docker layer cache makes reruns fast.
- [The fake drifts from Enable Banking] → It only covers what the API calls; the backend's unit tests use the same
  shapes (`tests/fakes.py`).

## Migration Plan

Tooling only.
